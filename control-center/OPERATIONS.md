# Operations as the operator models them

What the console shows under the Tasks and operations section, and where every value comes from. This file
lives next to the console because the monitor draws nothing that is not in one of the objects below;
when the operator changes, this file and `tasks.jsx` change together. Sources are the CRDs under
`operator/config/crd/bases` and the reconcilers under `operator/internal/controllers` on main.

## The shape every operation shares

Every `*Ops` kind in `storage.simplyblock.io/v1alpha2` carries:

| Field                                    | Meaning                                                                                                                     |
|------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------|
| `spec.action`                            | one value of the kind's enum, immutable                                                                                     |
| `spec.abort`                             | the only stop; honored at the abortable steps listed below, refused elsewhere (event `AbortRefused`)                        |
| `status.phase`                           | `Pending`, `Running`, `Succeeded`, `Failed`, `Aborted`                                                                      |
| `status.step.state`                      | the position in the action's step graph; `Completed` on success; a failed or aborted operation keeps the step it stopped in |
| `status.step.claim`                      | `{state, attempt, leaseUntil}`: the step's side effect was started                                                          |
| `status.step.deadline`                   | when the step expires                                                                                                       |
| `status.message`                         | one sentence, replaced as the phase changes; a `Pending` operation queued behind a lock says so here                        |
| `status.startedAt`, `status.completedAt` | lock acquired, terminal phase reached                                                                                       |

There are no `conditions` on any Ops kind, nor on StorageCluster, StorageNode, or StorageDevice.
Step entry time is not stored.

Locks: `status.activeOpsRef` on StorageCluster, StorageNode, StorageDevice, StoragePool,
ControlPlane, and StorageBackup names the one operation allowed to act; a second one stays `Pending`
with event `OperationQueued`. PersistentVolumeOps locks differently: the annotation
`storage.simplyblock.io/active-volume-migration` on the StorageCluster (one migration per cluster at a
time) and `storage.simplyblock.io/active-ops` on every PersistentVolume of the subsystem. Locks are
independent of each other: a cluster rolling restart takes no node lock, a node operation checks no
cluster lock.

## Control plane tasks

The control plane's task record (`TaskDTO` in `shared/openapi.json`) is flat: `id`, `cluster_id`,
`storage_node_id`, `device_id`, `function_name`, `function_params`, `function_result`, `status`
(`new`, `running`, `suspended`, `done`), `canceled`, `retry`, `max_retry`. It has no parent, master,
or subtask field, and no timestamps. The 28 `function_name` values are the openapi enum.

The operator keeps a window of the running and pending tasks in `StorageCluster.status.tasks[]`
(`id`, `type`, `status`, `retry`, at most twenty) and raises events `TaskCompleted`, `TaskCanceled`,
and `TaskGaveUp` when one leaves the window. The only task id it records on an object is
`StorageNode.status.nodeAddTaskID`. No operator code matches a task to a node or device; the console
may do so from the v2 record's `storage_node_id` and `device_id` when the control plane is readable,
and labels that correlation as such.

Cancel: `StorageClusterOps` with `action: CancelTask` and `spec.cancelTask.taskID`. There is no
other cancel route.

## How the monitor nests things

- An Ops object is one row. Its steps come from the kind's enum, in graph order, with the current
  one from `status.step.state`.
- Child rows are objects that name the parent: PersistentVolumeOps whose `spec.creatorRef` is the
  parent, or whose `storage.simplyblock.io/drain-node` label is the parent's node; the StorageClusterOps
  a ClusterDeploymentConfig owns; the StorageNodeOps a StorageNode's deletion created.
- Task rows under a cluster come from `status.tasks[]`; a task row is attached to an operation only by
  a recorded id (`nodeAddTaskID`, `relocate.volumes[].taskID`, `cancelTask.taskID`).
- Nothing else is a parent link. A task that merely coincides with an operation is listed under the
  cluster, with the operation named as running at the same time.
